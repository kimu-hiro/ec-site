# 07 コーディング規約を作る（マスト）

## 何のためか

お店の「作業のきまり」を紙に書いて、壁に貼る段。
「名前はこう付ける」「字下げはこう」「コメントにはこれを書く」を
先に決めておくと、13 から先のコードが、どのページも
同じ書き方でそろう。

- 課題の決まり：「自分で定められる、理解している範囲で OK」
- 新しく覚えること：PHP での名前の付け方（2つの書き方）
- 新しく入れるもの：無い

## できあがりの形

```
ec-site/
  └ 書類リスト/
      ├ 課題チェックリスト.md
      ├ 01_ページ一覧.md
      ├ 02_画面遷移図.png
      └ 03_コーディング規約.md   ← 今日作るのはこれ
```

## 1. もとにする物

PARA の `共通ルール.md` の「## コード」→「書き方」。
リーダブルコードから自分で作った決まりが、もうある。
これを写して、PHP に合わせて直す。

```
写す（共通ルール）
  ↓
PHP に合わない所を外す（手順 3）
  ↓
PHP と課題に合わせて足す（手順 4）
```

お手本を見たくなったら、課題文がすすめている
Google 検索「コーディング規約」で、5分だけ見る。
PHP の世界で広く使われている決まりには、
PSR-12（ピーエスアール12）という名前が付いている。
全部まねしなくていい。

- PSR ＝ PHP Standards Recommendation
  （standards＝標準、recommendation＝おすすめ）

## 2. ファイルを作って、見出しを並べる

`書類リスト/03_コーディング規約.md` を作り、
先に見出しだけ並べる（04 と同じやり方）。

```markdown
# コーディング規約

## 名前
## 見た目（字下げ・空白）
## 関数
## コメント
## ファイルと置き場所
## 安全のための決まり
```

見出しは、自分が分かりやすければ変えてよい。

## 3. 共通ルールから写して、合わない所を外す

`共通ルール.md` の「書き方」の行を、合う見出しの下に写す。
写しながら、PHP では使わない行は外す。

| 外す行 | 理由 |
|---|---|
| シェルの引数（`$1`・`$2`） | シェルの話 |
| `let` ではなく `const` | PHP に `let` は無い |
| useEffect | React の話 |
| `getElementById` の例 | JavaScript の話。残すなら PHP の例に変える |

残す行は、課題を見る人にも分かる言葉に直す。
（「僕」「ひろし」のような言葉は使わない）

## 4. PHP と課題に合わせて、決まりを足す

次の表の「決めること」を、1つずつ自分で決めて書く。
どちらを選んでもよい。選んだら、最後まで同じにする。

### 4-1. 名前の付け方

PHP の変数と関数の名前には、よく使われる書き方が2つある。

| 書き方 | 例 | 呼び名 |
|---|---|---|
| 小文字と `_` | `$user_name`・`get_product_list()` | スネークケース |
| 2語目から大文字 | `$userName`・`getProductList()` | キャメルケース |

- snake case ＝ 蛇の形（`_` で低くつながる）
- camel case ＝ らくだの形（大文字がこぶに見える）

ヒント：テキストの TRY56 は、どちらで書いてあったか。
テキストに合わせると、見比べるときに迷わない。

ほかに決めること：

| 決めること | ヒント |
|---|---|
| 定数の名前 | 全部大文字と `_`（`DB_NAME`）が多い |
| ファイル名 | 05 で決めた形（小文字と `_`）にそろえる |
| true/false の変数 | 共通ルールの `is`・`has` |

### 4-2. 見た目

| 決めること | ヒント |
|---|---|
| 字下げはスペースいくつか | テキストのコードは何個で下げていたか |
| PHP だけのファイルの終わり | `?>` を書くか書かないか（テキストに書いてあった） |

### 4-3. コメント

テキストの MVC の章で、関数の上に `/** */` の
特別なコメント（PHPDoc）を書いていた。
これを使うかどうかを決める。

### 4-4. ファイルと置き場所

課題で決まっていることを、規約にも書いておく。
（課題チェックリストの「実装要件」の所にある）

- どの係（Controller・Model・View）を、どのフォルダに置くか
- 定数をどこにまとめるか
- URL やファイルの読み込みは、絶対パスか相対パスか

### 4-5. 安全のための決まり

これまでに決めたことを、規約の形で書く。

- 画面に出すときは、何を通すか（XSS）
- DB に問い合わせるときは、何を使うか（SQL インジェクション）
- パスワードは、どの形で保存するか

## 5. 1行ごとに、短い例を付ける

決まりだけだと、読む人が迷う。
できる所は、よい例を1つ添える。

```markdown
- 変数の名前は小文字と _ でつなぐ
  - 例：$user_name
```

だめな例も並べると、もっと伝わる（なくてもよい）。

## 6. Claude に見せる

保存して「書けた」と Claude に伝える。Claude は次を一緒に見る。

- 自分で説明できない決まりが入っていないか
  （課題は「理解している範囲で OK」なので、
  分からない行は入れない方がよい）
- 課題チェックリストの「実装要件」と合っているか
- 例と決まりが合っているか

## 7. git に入れる

```bash
git add 書類リスト/03_コーディング規約.md
git commit -m "コーディング規約を作る"
git push
```

## つまずいたら

| 困ったこと | 直し方 |
|---|---|
| 決まりが多すぎて、守れる気がしない | 守れない行は消してよい。少なくても、守れる方が大事 |
| どちらを選べばいいか分からない | テキストに合わせる。迷ったら Claude に、2つの差を聞く |
| 共通ルールのどこを写せばいいか分からない | 「## コード」の「書き方」の所だけ。「進め方」は写さない |
